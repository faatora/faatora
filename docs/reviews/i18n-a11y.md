### 1.3 Arabic translation quality

Overall the Arabic copy is **native-sounding and consistent in register** (formal MSA, suitable for a B2B VAT product). The brand-name transliterations (كويك بوكس, زوهو بوكس, أودو, ساب, إكسل, تالي) follow accepted market practice and are fine.

Issues worth calling out:

- **"محال"** (`accountant.referred_badge`): meant to render as *muḥāl* "referred", but without short vowels this reads identically to *muḥāl* "impossible". A one-word badge is high-visibility. Recommend "عميل مُحوَّل" or at minimum "مُحال" with the shadda, or clearer "تمت الإحالة".
- **"لا توجد (شركات فقط)"** for *None (B2B only)* (`checker.b2c.0`): native but inconsistent with the question text that keeps the `(B2C)` acronym bracketed. Keep style parallel — either translate both acronyms or neither.
- **"إكسل" / "تالي"** (`checker.tool.excel`, `checker.tool.tally`): transliteration is fine; "تالي" is the only transliteration that is also a common Arabic word ("next"), so in a radio list rendered right after a button labeled "التالي" (`checker.next`) users may double-take. Low concern — flagging only because the two labels sit on the same screen.
- **"منشأة"** (tenant/entity): correctly used throughout — not the retail-ambiguous "تاجر" nor "عميل" (which here is reserved for the end-client of an accounting firm, correctly). Good discipline.
- **"ضريبة القيمة المضافة المُحصّلة"** for *VAT output*: natural; shows a translator who understood that "output VAT" is tax collected on sales rather than literal "ناتج ضريبي".

**Translation quality score — rough:** ~92 of ~120 strings read as natively authored (clean MSA, correct business register). ~25 are either transliterated brand names (expected, correct) or UI primitives (yes/no/back/next). ~3 feel slightly stiff or ambiguous (listed above). **No obvious machine-translation artifacts.** The three I'd flag as examples of imperfect-but-not-wrong phrasing: `accountant.referred_badge` ("محال"), `checker.b2c.0` (parallelism), and `checker.tool.tally` ("تالي" collision).

### 1.4 Numeric formats

- **OMR with 3 decimals (baisa):** every monetary render goes through a `money()` helper that calls `n.toFixed(3)`. `toFixed` always emits ASCII digits with a `.` decimal separator — so Arabic sessions do **not** accidentally produce Eastern Arabic (Arabic-Indic ٠١٢٣…) digits for financial values. Correct for VAT compliance.
- **Date on receipt:** `ReceiptView.tsx:37` uses `soldAt.toLocaleString(lang)` with `lang === 'ar'`. On most engines this returns Arabic-Indic digits AND the Hijri calendar variant depending on ICU data; result: receipts in Arabic mode may show date digits in a visually different style from the money columns. **Inconsistency, MEDIUM.** Recommend explicit `Intl.DateTimeFormat('ar-OM-u-nu-latn', {...})` to force Latin digits and Gregorian, matching the money fields and VAT regulatory expectations.
- **Progress "`{progressPct}%`" in CheckerPage.tsx:181** is already `aria-hidden="true"`, so SR announces `aria-valuenow`. Fine.

## 2. RTL correctness

### 2.1 DirectionProvider

- `components/DirectionProvider.tsx:12-18` sets `dir` and `lang` on `document.documentElement` (`<html>`) inside a `useEffect` keyed on `i18n.language`. **Correct.**
- **Caveat:** `apps/web/index.html` hard-codes `<html lang="en">` with no `dir`, and the direction is applied only after React mounts and the effect fires. There is a one-frame FOUC where Arabic markup renders LTR before the effect flips it. LOW/COSMETIC — add `dir="ltr"` to index.html for honesty and let i18next's `htmlTag` detector + the effect do the switch; or persist last-known language to localStorage and inline a tiny script that reads it before React mounts.

### 2.2 Physical direction utilities

A thorough grep for Tailwind physical-direction classes (`pl-`, `pr-`, `ml-`, `mr-`, `text-left`, `text-right`, `float-left`, `float-right`, `border-l-`, `border-r-`, `rounded-l-`, `rounded-r-`, `left-`, `right-`) across `apps/web/src`:

**Zero matches.** Every candidate was a false positive (`border-rose-200`, `rounded-lg`, `border-r-ose-200` substrings). All padding/margin/text-alignment uses logical siblings: `ps-`, `pe-`, `ms-`, `me-`, `text-start`, `text-end`.

### 2.4 Icon / glyph mirroring

- **Recommendations arrow `→`** (`ResultView.tsx:96`) is a hardcoded ASCII character inside an `aria-hidden` span. In RTL this still points **rightward**, which semantically means "backward" relative to reading flow — the arrow becomes a visual contradiction. Fix: either use the logical character `U+2192` only in LTR and `U+2190` in RTL, or (preferred) use `<span class="rtl:rotate-180 inline-block">→</span>` or a Lucide `ArrowRight` with Tailwind's `rtl:rotate-180`. MEDIUM.
- **Minus / plus** on qty buttons (`−` / `+`) are symmetric — safe either direction.
- **Blocker `!`** (`ResultView.tsx:75`) — symmetric glyph.
- **`+` in link-client button** (`AccountantPage.tsx:179`) — symmetric.

No other directional iconography in these files (no back-arrow glyphs, no play-triangles). Good.

### 2.5 Receipt layout for Arabic customers

`ReceiptView.tsx` is wrapped in `<section aria-label={t('pos.receiptTitle')}>` with `max-w-sm` (≈384 px) and `print:max-w-full`. All table cells use `text-start`/`text-end`, so columns flip correctly:

- LTR: `# | Item | Qty | Subtotal`
- RTL: `Subtotal | Qty | Item | #`

The flip is correct **except**:
- `<th>#</th>` (line-number column) remains visually at the start-edge in both directions, which is standard for receipts and matches ZATCA/Oman reference layouts.
- `font-mono` on the sale number is safe (digits-only).
- The `max-w-sm` print target may be slightly wide for a 58 mm receipt printer stock (≈ 220 px at 96 dpi); but the brief says 80 mm thermal is more common and 80 mm = ≈ 300 px, which fits. LOW — worth smoke-testing on real hardware.

## 3. Accessibility (WCAG 2.1 AA)

### 3.1 Semantic landmarks

- `App.tsx:40` wraps non-POS routes in `<main>`, with a top-level `<header>` containing brand + language toggle. 
- `PosPage.tsx:315` provides its own `<main>` and `<header>`. 
- **Gap:** when the POS route is active, `LanguageToggle` is not rendered anywhere. An Arabic cashier who lands on `#pos` without having set their language elsewhere has no in-UI way to switch. **MEDIUM.**
- No `<nav>` landmark anywhere; given the hash-based routing between three top-level screens, a `<nav>` with language toggle + route links would help SR users orient. Minor.
- Receipt uses `<section aria-label=…>` — acceptable.

### 3.2 Form labels

Every text input is associated with a `<label htmlFor>`:
- `CheckerPage.tsx` steps 1,2,3,4,7,10 — all have `<label htmlFor>` ✓
- Steps 5,6,8,9 use `<fieldset><legend>` — correct for radio groups ✓
- `AccountantPage.tsx:126-138` firm-name — labeled ✓
- `LinkClientDialog.tsx:70-86` tenant id — labeled ✓
- `LinkClientDialog.tsx:88-96` referred checkbox — wrapped in `<label>` ✓
- `PosPage.tsx:344-360` search — uses `<label><span class="sr-only">...</span><input>` + `aria-label` ✓
- `PosPage.tsx:488-498` tendered — wrapped in `<label>` ✓

**No unlabeled inputs.**

### 3.3 Keyboard navigation

- Every actionable element is a real `<button type="button">` (or `<a>` for the landing CTA). No `onClick` on `<div>`/`<span>` without `role="button"`. ✓
- CheckerPage radios inside `<fieldset>` — natural arrow-key navigation works. ✓
- POS "add product" tiles are `<button>` elements with `role="listitem"` nested in a `role="list"` parent. **Note:** ARIA says children of `role="list"` should be `role="listitem"` or `<li>`, but authoring `<button role="listitem">` is unusual and some SRs mis-announce. LOW — consider restructuring as `<ul>`/`<li>` with the button inside, or drop the explicit roles since the grid is already visually scannable.
- Qty +/– buttons are reachable by tab. ✓
- LanguageToggle buttons are reachable and use `aria-pressed`. ✓

### 3.4 Focus management

Several gaps:

- **CheckerPage stepper** (`CheckerPage.tsx:140-147`): clicking Next/Back changes `step` state and re-renders `StepBody`, but focus stays on the Next/Back button. For a form flow, focus should move to the new question's `<label>` or first interactive element so SR users immediately hear the new step and keyboard users don't have to tab back up. **MEDIUM.**
- **POS complete → receipt** (`PosPage.tsx:299-307`): when `completedSale` becomes truthy, the page swaps to `ReceiptView`. Focus stays on the (now-unmounted) Complete button. **MEDIUM.** Add a ref + `focusAfterMount` on the Receipt heading, or move focus to the Print button.
- **ReceiptView → New sale**: same symmetrical issue — clicking "New sale" doesn't restore focus to a sensible target in PosPage.
- **LinkClientDialog**: focuses first input on open (good, `LinkClientDialog.tsx:27`) BUT:
  - No **Escape** key handler to close.
  - No **focus trap** — tabbing past the Link button lands on page-background elements behind the overlay.
  - On close, focus is not restored to the triggering "Link client" button in AccountantPage.
  **HIGH** — a modal dialog that isn't keyboard-trappable fails WCAG 2.4.3 (Focus Order) and 2.1.2 (No Keyboard Trap works the other way, but keyboard users expect Escape).

### 3.5 Screen-reader live announcements

- **CheckerPage submit**: `submitError` has `role="alert"` (`CheckerPage.tsx:202`) — good. But `submitting` state (button changes label to "Submitting…") has no `aria-live` region, so SR users must re-poll the button text. LOW.
- **ResultView**: wrapped in `aria-live="polite"` (`ResultView.tsx:39`) — good.
- **PosPage**: `notFoundCode` and `productsError` have `role="alert"` — good. **However, sale completion (`completedSale` set → ReceiptView swap-in) has no `aria-live` announcement.** SR user clicks Complete sale, screen pivots, nothing is announced. **MEDIUM.**
- **PosPage online/offline badge** has `role="status"` — good. The `aria-live` is `polite` by default on `status`. ✓
- **AccountantPage** error states use `role="alert"` consistently. ✓

### 3.7 LanguageToggle — `aria-pressed`

`LanguageToggle.tsx:21,29` toggles `aria-pressed={current === 'en'}` and `aria-pressed={current === 'ar'}` on two sibling buttons inside `role="group" aria-label="Language"`. This is semantically correct for a two-state toggle group, but a more conventional pattern for a mutually-exclusive language picker is `role="radiogroup"` with child `role="radio" aria-checked`, or a native `<select>`. `aria-pressed` on sibling toggle buttons works, just slightly unusual. LOW. The `aria-label="Language"` on the group is the HIGH issue flagged in §1.2 — not translated.

### 3.8 LinkClientDialog detail

Covered in §3.4 — missing Escape handler, no focus trap, no focus restoration on close. HIGH.
