# ADR-0002: EP4 Clearance, Archive, Compliance, Console and Observability

- Status: Accepted
- Date: 2026-10-17
- Deciders: A3-A17 module owners; A17 architecture review
- Supersedes: nothing
- Context of: ADR-0001 (tenancy, invoicing primitives, signing port)

## Context

EP4 took Faatora from "a tenant can draft, sign and look at an invoice" to "a tenant's signed invoice reaches the OTA via an ASP, is archived for ten years, and the operator can watch all of that happen from Prometheus". Across the epic we made eight architectural choices that are not in ADR-0001 and need to be written down because the next six months of work (real ASP wiring, S3 archive, accountant console GA, Wave 4 scale) will all build on them. This ADR records those eight.

Every decision below was made against the same three constraints: tenant isolation must never depend on application code remembering to filter, the clearance path is a tier-0 compliance product and its SLOs are externally promised, and the compliance core must be swappable rule-pack-by-rule-pack without touching the service layer.

## Decisions

### D1. Clearance pipeline topology: outbox → scheduler → provider → callback

A signed invoice emits exactly one row into `clearance_outbox` inside the same transaction that flips the invoice to `SUBMITTED`. The row's `idempotency_key` is the invoice's `document_uuid`, and the column carries a `UNIQUE` constraint — `INSERT … ON CONFLICT DO NOTHING` is therefore a hard idempotency guard, not an application-layer compare-and-set. A cron-driven `ClearanceScheduler` fires `drainOnce` every 10 s with a reentrancy flag that drops overlapping ticks. `drainOnce` reads candidate `(id, tenant_id)` tuples through a `MIGRATION_DATABASE_URL`-bound pool that bypasses RLS, then processes each row under `withTenant(db, tenant_id, …)` so every INSERT / UPDATE is still RLS-filtered. The `TransmissionProvider` port is the only contract the ASP has to satisfy; the stub lives in `stub-asp.ts`, the production adapter is a drop-in. OTA verdicts can be synchronous (`cleared` / `rejected`) or asynchronous (`accepted_pending` → later `handleCallback`). Both paths are state-machine-asserted and idempotent against the invoice's current state.

Scheduling cadence (10 s) was picked to meet the p95 < 10 s clearance SLO in `docs/sla.md` while leaving headroom; drain `LIMIT` was set to 50 — enough for Wave 3 load, intentionally low enough that a stuck row doesn't delay the next tick by minutes.

### D2. State-machine ownership model (one owner per transition)

The invoice lifecycle is split so each transition has exactly one owning module and no module reaches across a seam:

- `DRAFT → VALIDATED` is owned by `InvoicesService.issue` and happens after the compliance port returns `ok`.
- `VALIDATED → SIGNED` is owned by `SigningService.sign` and happens after a successful `Signer.sign`, within the same transaction that inserts the `signed_documents` row.
- `SIGNED → SUBMITTED` and `SUBMITTED → CLEARED | REJECTED` are owned by `ClearanceGatewayService`, with the SUBMITTED transition happening transactionally with the outbox insert and the terminal transitions driven either by a synchronous ASP response (actor `system`) or by an async callback (actor `asp_callback`).
- `CLEARED → ARCHIVED` is owned by `ArchiveService.archiveInvoice`. The current wiring exposes this transition as a user-triggered endpoint; the EP4 review flagged auto-triggering from the gateway as a Wave-4 BLOCKER.

The `assertCanTransition(from, to, actor)` helper in `state-machine.ts` is called before every UPDATE and before every `clearance_events` insert. The actor allowlist is per-transition: `SUBMITTED → CLEARED` accepts `system` and `asp_callback` but not `user`, so a human can never manually clear an invoice.

### D3. Compliance package layered architecture: canonical → EN 16931 semantic → PINT-OM → UBL

The compliance core is layered so that a sibling pack (KSA, UAE) is additive, not a fork of the type graph. `canonical/types.ts` is the local shape produced by the API and validated by zod. `semantic/en16931.ts` is the EN 16931 "pay once, specialise many times" middle layer, with semantic business-term identifiers (BT-1 … BT-153, BG-22 … BG-25). `pint-om/types.ts` and `pint-om/specialize.ts` carry the Peppol PINT-OM customisation. `ubl/serializer.ts` is a deterministic (object-key-insertion-order) UBL 2.1 writer. The `validate/pipeline.ts` entry point threads the four stages: canonical zod → canonical→semantic → VAT-math integer-baisa rebuild → semantic→PINT-OM → PINT-OM→UBL → XSD-lite → Schematron-lite. A single `rulePackVersion` string (`PINT_OM_RULE_PACK_VERSION`) threads through so an invoice can be persisted next to the exact rule-pack it validated against.

Severity split: EN-16931 and BR-CO-* rules are hard errors; OM-local rules that could legitimately differ in cross-border scenarios (BR-OM-001 VATIN format, BR-OM-002 non-OMR currency) are warnings; BR-OM-003 (future issue date) is a hard error.

### D4. Archive hash-chain scheme

Each `archive_records` row stores three hex-encoded SHA-256 fields: `sha256` (the hash of the archived signed-XML bytes), `prev_sha256` (the `sha256` of the previous row for THIS tenant in `archived_at` order, null for the first), and `chain_hash = sha256_hex(utf8(prev_sha256 ?? '' || '|' || sha256))`. The chain is per-tenant: tenants are isolated by RLS and each one's rows form an independent chain. The `|` separator is explicit so a null-prev row cannot be confused with a prev whose hex prefixes `sha256`. Verification recomputes `chain_hash` for every row in archived_at order; divergence surfaces at the first altered row.

The filesystem backend writes `${baseDir}/${tenantId}/${YYYY}/${MM}/${documentUuid}.xml` with mode `0o400` and the `wx` open flag, giving create-only immutability on the storage side; production S3 pairs this with Object Lock in COMPLIANCE mode for the full 10-year retention. The `ArchiveStorage` port makes the backend swap trivial, provided its two methods (`put`, `get`) are the only shape the service presumes.

### D5. Accountant console's dual-guard split

The accountant console serves firms that work across many client tenants. Requiring an `x-tenant-id` header for every console request would force the firm's UI to carry a tenant switcher on every page and complicate the common "find my client" flows. We therefore split the HTTP boundary into two guards: `TenantGuard` for every tenant-scoped controller (requires `x-tenant-id`, verifies membership, attaches tenantId to the request, drops into `withTenant` at the service seam) and `AccountantAuthGuard` for the console (requires only the Cognito token, attaches `userId` + `email`, does NOT bind the request to any one tenant). Services called from the console must explicitly open a `withTenant` context for every client-tenant data access they make — RLS still filters, but the service, not the guard, chooses which tenant to scope to and may legitimately cross tenants in one logical operation (e.g. "list all my clients' invoices this month"). This decision moves the trust boundary from the guard to the service layer for the accountant plane, and that boundary is enforced by `AccountantService.assertFirmLinkedTenant` or the equivalent per method.

### D6. B2C 24-hour batching in POS: sale → aggregate invoice → clearance

Retail (POS) sales do not fit the one-sale-one-invoice OTA model economically or ergonomically. We instead persist every B2C sale in `pos_sales` + `pos_sale_lines` tagged `clearance_status = 'PENDING_BATCH'`, and once per day (or on operator trigger) `SalesService.batchPendingToInvoice` groups all `PENDING_BATCH` sales up to a cutoff into one `invoices` row with one line per `(vat_category, vat_rate)` aggregate and `number = B2C-YYYYMMDD-NNN`. The aggregate invoice flows the same `DRAFT → VALIDATED → SIGNED → SUBMITTED → CLEARED` path. The B2C aggregate buyer is an auto-provisioned `parties` row named "B2C aggregate" so FK + RLS + the compliance pipeline all accept the row without special-casing. Sales marked `BATCHED` carry their invoice id so a Z-report can reconstruct the retail-to-regulator mapping.

### D7. `StubAspProvider` is the Wave 3 default, NOT a production class

`ClearanceModule` wires `TRANSMISSION_PROVIDER` to `StubAspProvider`. The stub cache-keys on `idempotencyKey`, understands a `<ForceReject>true</ForceReject>` body for deterministic rejection tests, and in `STUB_ASP_MODE=async` schedules a `setTimeout(50ms)` callback into the gateway's own `handleCallback`. It is deliberately in-memory and process-local so our Wave 3 tests are hermetic. Going live requires replacing exactly one DI binding; the port's three result shapes (`cleared` / `rejected` / `accepted_pending`) are the invariants that production adapters must preserve.

The stub is explicitly NOT a production class: its idempotency cache does not survive restart, its callback is in-process, and it cannot represent transport-level failure modes (TLS, DNS, rate limits). Running it in production is a release-blocker regression.

### D8. Observability tier-0 flag: canary + queue-depth sampler + per-tenant metrics

The product's SLO page commits to a 15-minute MTT-ack and a 60-minute MTT-mitigate on page alerts. Three observability components are therefore classified tier-0 and shipped alongside the clearance pipeline, not after it:

- A **synthetic canary** fires every 60 s, runs `SELECT 1` against the app pool AND runs a tiny canonical fixture through `@faatora/compliance.validateCanonical`, stamps `faatora_canary_last_success_timestamp` on success, and emits a `page` alert on failure. Alerting is on `time() - faatora_canary_last_success_timestamp > 300`.
- A **queue-depth sampler** reads `clearance_outbox` grouped by `status` and `COUNT(*) FROM clearance_dlq` every 15 s through the same superuser pool the drain uses, and sets `faatora_clearance_queue_depth{status}` and `faatora_clearance_dlq_size`. It zeros statuses that disappeared from a round so a drained queue doesn't leave a stale gauge.
- **Per-tenant metrics** on the three business counters (`faatora_invoice_issued_total`, `faatora_clearance_submissions_total`, `faatora_signing_total`) carry a `tenant_id` label so the on-call can drill down from "the fleet SLO is burning" to "customer X is the one bleeding" without a code change. Latency histograms deliberately omit `tenant_id` so cardinality stays bounded.

The alert sink is a swappable port (`AlertSink` / `ALERT_SINK` DI token); the `LogAlertSink` is the DI default and `WebhookAlertSink` is rebound in production via `FAATORA_ALERT_WEBHOOK`.

## Alternatives considered

- **"Direct push" clearance without an outbox.** Rejected: an invoice signed and then lost between commit and HTTP response would silently never reach the OTA, violating the 99.95% clearance SLO. The outbox makes "committed" and "safely transmittable" the same moment.
- **One state-machine class that owns every transition.** Rejected as premature coupling — the lifecycle has four natural owners (invoicing / signing / clearance / archive) and spreading the transitions across them lets each team evolve its own branch of the lifecycle. The shared `assertCanTransition` recovers the "single declaration" benefit without the god-class drawback.
- **Fold EN 16931 and PINT-OM into one layer.** Rejected: KSA (ZATCA) and UAE (upcoming) both diverge from PINT-OM but share the EN 16931 semantic layer. Collapsing the layers would make a sibling-country pack a fork.
- **Append each invoice's hash into a single global chain.** Rejected: a single compromised row would invalidate every tenant's chain. Per-tenant chains compartmentalise the blast radius.
- **A single `AuthGuard` that reads an optional `x-tenant-id` header.** Rejected because the "optional" branch makes it too easy for a controller to forget to scope and leak cross-tenant data; two guards with two different contracts make the omission a compile error (the handler asks for `AuthContext` vs `AccountantAuthContext`).
- **POS sales reaching the OTA one-by-one.** Rejected on both economics (ASP fee per submission) and OTA guidance (aggregate B2C invoicing is explicitly allowed). The aggregate invoice path keeps the retail UX fast and still reconciles end-to-end.
- **Running the stub-ASP as a conditional branch inside the real adapter.** Rejected: putting the test double behind the same class risks it leaking into production via a config flip. Keeping it as a separate port implementation makes "which class is wired?" a one-grep answer.
- **Observability as an operator add-on (Wave 4).** Rejected because tier-0 means the SLOs are externally promised in Wave 3, and the operator cannot acknowledge an alert in 15 minutes if the alert does not exist yet.

## Consequences

**Positive.**

- The clearance path survives crashes (outbox) and transient ASP failures (circuit breaker + retry + DLQ) without manual intervention.
- The compliance core can be upgraded, replaced, or extended for a sibling country by publishing a new package version; the service layer only needs to update the port wiring.
- The archive is tamper-evident per tenant and verifiable in a single endpoint call.
- The accountant console can be built out as a sibling UX without re-architecting the tenant plane.
- Operators get a tier-0 dashboard surface from day one — the canary tells them the pipeline is alive, the queue-depth gauge tells them it is keeping up, the per-tenant counter tells them which customer to call.

**Negative / to be funded by Wave 4.**

- The outbox-and-drain pattern biases the architecture toward "eventually transmitted" semantics; callers who want synchronous OTA confirmation have to poll `GET /clearance/invoices/:id/status`. UX for that polling has not been designed.
- Per-process circuit breaker and in-memory stub-ASP idempotency are explicit Wave-3 compromises. The former becomes incorrect at >1 replica and must be shared; the latter is only acceptable while the stub is the provider.
- The `CLEARED → ARCHIVED` transition is declared but not auto-driven. Wave 4 must wire the archive hook into the gateway's cleared branches to deliver the 10-year archive SLO without a human in the loop (A17 architecture review BLOCKER B1).
- The compliance pipeline currently runs against placeholder party data because the adapter in `apps/api` doesn't resolve `parties` rows before calling the port (BLOCKER B2). Fixing this is a one-day change to `invoices.service.issue` and `compliance.pipeline.ts`.
- Per-tenant metric cardinality is bounded by the known tenant list; onboarding a thousand tenants will require migrating `tenant_id` off the HTTP counter (`faatora_http_requests_total`) and onto a sampled label set.
